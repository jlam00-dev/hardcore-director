# 硬核导演3.0远程制作工作流

电脑保持在线并推进获准任务，分镜及成片发到用户自己的飞书或微信审核。两种通道接入同一套本地制作流程。当前通过即梦画布执行真实生成，MiniMax Design用于能力检查和受限准备。

首次使用可查看安装、即梦登录、飞书配对、微信接收人与运行指令。本文件面向负责配置和操作本地流程的Agent。[使用手册](../support/user-guide.md) · [账号接入与运行手册](../support/remote-setup-guide.md)

## 核心链路

`需求 → 剧本 → 分镜/执行脚本/提示词 → 确认方案与生图预算 → 生成独立分镜图 → 手机逐镜审图 → 批准视频预算 → 逐镜生视频 → 规格检查与顺序合成 → 成片终审`

使用 [director_workflow.py](../../scripts/director_workflow.py) 的本地状态机。先运行 `--help`，再看当前子命令帮助，不猜配置字段。项目数据库与素材存用户选择的私有状态目录，不放进Skill目录、Git仓库或发行包。

实际验证范围随路径分别记录。即梦＋微信通过真实单镜闭环，飞书通过既有媒体的收发与审核，飞书“同意”与微信“拒绝”分别完成0费用两字测试。多镜真实付费、飞书审核后重新生成视频的完整Engine流程，以及新合成阶段的两端真人审核仍待实测。[制作联调记录](../../audits/workflow-v3.0.md) · [两字审核记录](../../audits/short-reply-v3.0-rc.9.md)

## 创作和计划

完整项目先走 [创作协作链](creative-collaboration.md)，按编剧诊断、导演调度、[分镜交付](storyboard-package.md)、声音cue及[模型路由](../prompt-tools/model-router.md)逐阶段交接。不要把“分镜脚本”和“提示词”当作两套互不关联的故事：它们是同一份逐镜事实的不同表达。

已有协作项目包时，先运行 [creative_handoff.py](../../scripts/creative_handoff.py) 的当前帮助并检查依赖、时间、状态与素材引用，导出新路径的零预算草稿，再通过 `director_workflow.py plan --file` 载入。编译产物没有审批或实时模型能力证明，仍停在方案审核；用户明确批准后才按原流程继续。创作项目里的声音/EDL是意图与交接，不能扩大执行器的自动剪辑、配音或素材上传权限。

当前Engine仍按先分镜图、再手机审图与生视频的顺序运行，每镜保留 `image_prompt`。纯文字T2V提示词可以作为创作产物，但导入草稿不表示执行器已支持跳过分镜图/审图直接生成视频；实际输入模式仍须按原工作流和实时合同核对。

运行时计划的创作Schema为 [workflow-plan.schema.json](../support/workflow-plan.schema.json)。`screenplay` 保存故事/对白，`shooting_script` 保存制作顺序，`shots` 包含稳定镜号、图像/视频提示词、时长、叙事目的、起止状态和用户提供的参考素材。机器Schema不检查实际叙事品质或成片相似度；多镜头时序仍使用[分镜机器门禁](storyboard-quality-gates.md)。

可选 [planner.py](../../scripts/hc_workflow/planner.py) 使用官方 `codex exec` 生成结构化计划；默认只返回待批准的规划请求。用户明确允许模型使用后才执行，可能消耗宿主额度。它不自动批准计划、预算或上传，也不启动媒体生成。规划进程使用临时工作目录、只读沙箱、不导入全局配置；这不是完整操作系统隐私隔离，仍须在预期的系统用户下部署。[官方命令文档](https://learn.chatgpt.com/docs/developer-commands#codex-exec)

## 执行器：先发现能力，再选择账号与项目

- **即梦**：当前适配官方 `dreamina-canvas`，不是把网页按钮坐标写死。用户自行用官方登录流程授权；profile/区域/空间与账号绑定。每次读取当前CLI Schema、模型能力、素材要求、会员与报价，再保存和运行。安装着另一个 `dreamina` CLI 不代表两者共用登录态。由CLI管理认证，不导出凭据。未安装时给出安装入口，不自动安装。
- **MiniMax Design**：通过用户本机桌面应用的MCP，不伪造不存在的同名CLI。用户自行启动、登录并选择专用项目；先列项目，再打开明确选定的项目，使用实时能力合同。不得默认打开第一个项目或复用用户当前的无关项目。执行、费用确认、查询和结果读取是不同操作，能力不足时明确停下。当前只读发现的合同为协议 `2025-03-26`、28个工具；仍缺少可证明的账号核验、硬费用上限和媒体 `execute` 调用方幂等保障，自动付费路径继续关闭。工具数量或 `confirm_cost` 的存在不能替代这些门槛。
- 供应商、账号或项目变化会使旧批准失效。无法自动核验账号时不得标记为已核验；受限人工确认模式必须明确显示其局限，不能默认为自动可信。

只写原创适配代码，不复制本机第三方Skill的私有创作资料，不打包其二进制或用户认证缓存。

### MiniMax Design阶段映射与受限准备

执行器配置必须明确 `project_id`，并在所用阶段的 `stages.image` 或 `stages.video` 提供 `capability_id`、`params` 和 `design_output`。阶段块仅支持这三个字段，额外的 `max_cost`、`budget` 等字段会明确拒绝，不能静默当作已生效的硬费用上限。实时合同的 `operation` 必须与图像/视频阶段及能力标识一致；不得把工作流项目号、网页昵称或本机素材路径当作Design能力或素材版本标识。配置快照深度固定进操作和审批绑定。由项目A改到B，即使在相同修订重新批准，也不能复用A的旧操作；必须重新规划并重新批准，避免改变已有操作的目标。

准备阶段只校验已审阅的参数Schema和平铺 `paramRules`，返回原提示词及参数的 `request_preview`，明确 `design_draft_saved=false`、`generation_submitted=false`。它不自动修改提示词、不写Design文档、不上传素材。未知规则、引用或非零最低媒体需求，以及会触发引用规则覆盖的模式继续停在 `needs_setup`，不猜测兼容性。可见项目不等于已打开；探测分别报告两者，账号仍标为未核验，提交仍被 `bounded_execute_unavailable` 阻断。

对官方Design 4.0.6（build 4.0.6.140）v3外部MCP的静态代码复核显示：媒体 `execute` 会交给gateway执行并等待任务，费用确认取决于余额和提醒/批次条件，余额足够时可能直接提交付费任务。`confirm_cost`只保护已进入确认流程的报价变化或过期，不保证每笔任务提交前都等待批准。此为该版本的静态结论，未进行真实付费试验；继续保留付费门禁，不用“先试execute取价格”的方式探测费用。

专用项目已由用户明确授权创建并亲自打开，可读取H3、Seedance 2.5、Wan等模型合同及本地 `merge_videos` 能力。已通过官方插件将用户批准的纯文字生产稿写入专用分组，`document_write` 使用调用方 `requestId` 保证幂等，随后 `composition_get` 回读可用，1829字节与批准预览的SHA精确一致。这是插件层文字写入与回读实测，不是Engine端到端新生成；本轮模型调用、媒体上传和费用确认均为0，不能把媒体 `execute` 的幂等缺口泛化到文档写入。

当前探测的目标项目可见且已打开，但 `account_verified=false`、`generation_contract_verified=false`；仍受 `account_identity_unavailable`、`no_pre_execute_quote`、`no_caller_submit_id` 限制。已在官方签名的MiniMax Design 4.0.6安装包中定位并完整读取与 `mcp-tools-v3` 匹配的v3随附模型卡，覆盖MiniMax、Seedance、Wan和GPT Image；这不证明运行时用户 `knowledgeDir` 指向同一目录，模型提示词适配及新请求仍未实测，已批准的外部纯文字稿保持原样。

需要Design专属提示词时，先核对客户端版本与MCP配置，再读取匹配版本官方安装包随附的必要模型卡；不得跨版本猜路径或把整个卡复制进本包。无法定位匹配来源时停下说明缺口。模型卡只提供创作指南，不授权上传、生成或扣费；读取卡或使用本包通用提示词工具都不等于新的模型请求已验证。

## 用户自助入口

在Skill根目录运行以下检查；这些命令默认不读取凭据、不登录、不发消息、不收费：

```bash
python3 scripts/workflow_login.py --doctor
python3 scripts/feishu_setup.py --doctor
python3 scripts/workflow_bridge.py --channel wechat --doctor
python3 scripts/workflow_bridge.py --channel feishu --doctor
```

微信扫码向导是 [workflow_login.py](../../scripts/workflow_login.py)。用户明确执行 `wechat --begin` 才申请官方二维码，`--wait` 只等待同一份授权；使用自己选择的绝对私有路径传 `--credentials-file` 和 `--challenge-file`。登录材料不允许存在仓库或共享临时目录，凭据文件0600、新目录0700。若需手机数字验证，使用标准输入入口，不能把验证码放命令行参数。不会安装或读取OpenClaw配置。

飞书自助向导是 [feishu_setup.py](../../scripts/feishu_setup.py)，使用已审阅的官方 `lark-oapi 1.7.5`，缺依赖只报告，不自动安装：

1. 在自己的飞书租户创建自建应用并启用机器人。本人私聊测试仅需租户权限 `im:message:send_as_bot`、`im:message.p2p_msg:readonly` 和 `im:resource`，不要顺带扩大到通讯录或群消息。
2. 用户在本机交互终端显式执行 `--configure --credentials-file`，自行指定绝对私有路径并输入App ID/Secret，均不回显；不能通过聊天、命令参数或管道传Secret。父目录0700、文件0600，拒绝Skill/Git目录、共享临时目录和符号链接。
3. 显式执行 `--pair --credentials-file` 并保持终端运行；本地官方SDK上线后，在控制台保存长连接方式、订阅 `im.message.receive_v1`，创建仅本人可用的内部版本并完成租户审核，不开启对外共享。向导不会代为创建或发布应用。
4. 本人向机器人私聊发送终端显示的一次性配对口令，再在终端输入“确认绑定”。匹配应用、用户私聊及口令后才保存单一审批人与单一会话；未配对文件不能用于运行bridge，重新绑定需显式 `--rebind`。向导不发消息、不读素材、不启动生成。

配对向导区分“正在尝试连接”和SDK实际连接已建立；连接开始关闭、断开或接收循环停止时立即判为失败，不能因子进程仍存活而继续显示在线。此类控制状态不受普通诊断提示去重限制。确认结果仅返回安全原因码，不记录输入原文；一次性口令和“确认绑定”仍逐字匹配，不使用模糊匹配，也不以新诊断结果反推历史取消原因。

桥接器仅在显式 `--run` 后加载用户选定的 `--wechat-credentials` 或已配对的 `--feishu-credentials` 私有文件；也保留用户自行设置环境变量的路径。微信首次发起私聊可建立可回信上下文；进程重启或上下文过期后可能需再次给机器人发消息。启动时指定已有项目、自己的状态库和素材根目录，`--resume-authorized` 才开启调度，仍不会自动批准预算。登录和连通性不代表已有内容上传授权。

微信扫码文件目前只向桥接器加载机器人令牌与机器人身份，不自动设置收件人与审批人。Agent仍需在本机核实用户本人的稳定peer ID，并显式配置 `HC_WECHAT_RECIPIENT`、`HC_WECHAT_ALLOWED_CHATS`、`HC_WECHAT_APPROVERS`；昵称不能代替该身份。本包尚无与飞书等价的微信本人配对向导，不宣称扫码即完成审核绑定。

桥接器不带 `--resume-authorized` 时只监听和消费审批，不主动投递待审事件；事件投递由Engine调度触发。只发零预算内容审核前，须核对生成范围为空、禁止供应商上传且无有效生成批准。`director_workflow.py doctor` 可调用配置的真实供应商查询身份及能力并打开本机状态库，不属于上述离线检查。

当前运行CLI没有独立的只取报价子命令，不能用已获生成批准的调度器试探价格。Agent先按当前官方CLI合同保存专用草稿，再执行 `node quote`，此阶段不调用 `node confirm` 或 `node run`。真实图生视频报价须使用对应已审图片；无图文生视频或假占位图报价不能替代。

真实执行器还需通过桥接器的显式 `--config` 传入与项目一致的 `providers` 配置：账号profile、选定画布/项目、图像和视频模型及参数。另用 `--generation-provider` 明确选择本次执行器。不要把工作流项目编号误当云端画布ID；不默默使用缺省配置接管其他项目。离线doctor不读取该配置文件，认证仍交由用户自己的官方CLI或环境变量管理。

微信实际接收进程在首次轮询前按官方实现通知后端启动；通知失败只提示检查，不冒充登录失效。消息游标按机器人身份隔离，保存在用户自己的私有审批库，整批处理成功后才推进；保存失败立即停止接收，重放消息仍经事件去重。游标不是回信上下文，不持久化 `context_token`，也不把启动通知成功当作消息送达证据。

可用 [离线示例计划](../support/workflow-plan.example.json) 演练状态机。用 `director_workflow.py init` 创建模拟项目，`plan --file` 保存示例，再按顺序 `approve --stage plan`、`tick`、`approve --stage storyboard`、`tick`、`approve --stage final`。每次批准要求明确actor；例子生成的是模拟JSON，不是分镜图或视频。真实审核图像、模型费用与手机回传须另行联调。

## 手机端审核

- **飞书**使用用户自己的自建应用、机器人、App ID/Secret与审批人白名单。官方SDK长连接支持接收本人私聊的“同意／拒绝”，并向同一会话发送分镜及审核消息。
- **微信**：仅使用腾讯官方开放的机器人接入及其扫码流程；不提供个人号外挂、私有协议逆向或获取微信登录Cookie的方案。文本审核、图片/文件回传分别按真实能力开关；缺少媒体依赖或授权时须明确报告，不把文字通知当作图像或视频已送达。
- 每个用户自己配置接收会话与审批人。消息事件只入队，不能直接在网络回调里执行生成或Shell。非白名单发送者、错会话、旧版本、过期或重放审批全部拒绝。
- 审批绑定项目、修订、分镜/素材哈希、具体动作、供应商/账号、上传范围、预算及一次性随机挑战。手机显示人能读懂的内容和金额，不能只给一串摘要要求盲批。
- 引擎自动为每镜发送独立审核图与指令；拒绝某镜只返工该镜，保留其他镜头与历史记录。相同修订和绑定的互不重叠镜头审核可同时有效；范围重叠、整批审核、账号/接收人或版本变动会替换旧挑战。修改后重新审核对应版本，不用旧“OK”覆盖新内容或新的扣费。
- 内容同意与费用批准可以分两次。只审图的请求显示0预算，生成和上传范围为空。同意后等待生成授权，取得有效报价后再发送绑定同一版本、素材与费用上限的请求。3.0的两字审核消息成功送达后，用户可回复“同意”或“拒绝”。多项待审、内容变更或上一项已处理时，先选编号并重新展示范围与费用，再由用户决定。选择编号只定位请求，重复同意不会转批下一项。原长指令保留兼容。
- 两字回复上下文按通道、机器人实例、本人及会话隔离，保持原修订、镜号、素材绑定、范围、预算、有效期和一次性消费；历史请求不自动开启新方式。过期、旧引用、来源时间无法可靠核验或上下文已变时暂停澄清。回执仅表示已记录并等待工作流核验；API回信失败不撤销已入队决定，也不重新消费审批。
- `normalize_cfr` 另设 `composition` 审核阶段：所有视频就绪后才请求本次新批准，预算为0、生成范围为空且禁止上传。批准精确绑定项目、修订、计划哈希、有序视频素材哈希及每段时长、统一规格策略；策略、素材或顺序变化使旧批准失效。既有内容同意及历史生成授权的宽免不能授权重编码。rc.6已完成本地Engine验证，此新阶段的微信/飞书真实收发及真人批准尚未实测。

飞书已用用户明确授权的既有PNG和4秒MP4完成真实收发：两个独立审核挑战、两条不同的入站消息均匹配单一审批人与会话，绑定阶段、修订和素材，生成范围为空且预算为0；两项审核均应用成功。联调所用本地素材字节哈希与原件一致，测试后未改动，用户确认图片可打开、视频可正常播放。本轮没有调用模型生成，也未检验飞书审核后重新生成视频的完整Engine流程；私有诊断和联调脚本未作为本包组件交付。配对中曾有一次确认阶段取消，随后在用户明确授权后由助手协助本机最终确认，因此不能描述为完全自助、无人介入。

## 费用、恢复和本机边界

1. 方案通过、允许上传、允许生图、允许生视频是不同范围。预算按供应商的真实单位计，不将人民币与积分混算，不以余额当授权。累计预留防止多镜头共用上限穿透；提高质量、数量、重做或预算都需新批准。
2. 调用前持久化业务身份和阶段，受理不等于成功。响应丢失、重启或超时只查询原任务，不自动重发生成。无法按ID查证的情况保持未知并要求人工恢复。
3. 公共任务状态不保存访问令牌、费用确认token、临时签名URL或供应商内部存储标识。账号凭据由官方CLI或用户独立环境保管；微信会话凭据需要私有、受限的专用存储，不得进入通用日志和Git。
4. 用户电脑需保持在线、应用和工作进程可用，休眠会中断运行。不自动更改系统休眠、电源、登录项或防火墙，也不默认建立公网隧道。
5. 每份审批库只允许一个协调进程消费。恢复时仅重新处理本次明确选定项目、仍有效且已接收的审核；再次校验内容、账号、范围和累计预算，继续使用原操作ID。进程排他与安全重放防止重复生成，不把两个数据库之间的处理宣称为严格的“恰好一次”。协调调度可停止，但网络监听不保证随协调锁释放而退出；当前飞书SDK监听未实现协作停止，独立验证须用受控子进程限时运行，并以terminate/join完成清理。

## 基础合成，不是自动剪辑

[compositor.py](../../scripts/hc_workflow/compositor.py) 只按获准镜头顺序拼接本地成功视频。先核验文件哈希、真实媒体、时长、画幅、帧率和音轨兼容。计划的可选 `composition.mode` 仅接受 `stream_copy` 或 `normalize_cfr`，缺省仍为保留原时序的 `stream_copy`，不新增普通合成审批；不能直接顺序封装时返回待处理，不静默重编码。

`normalize_cfr` 在所有视频就绪后，由Engine取得独立、有效的新 `composition` 批准，才从原片制作统一规格副本。手机需展示H.264 CRF18、yuv420p、计划FPS与每段计划时长。改变FPS可能复制或丢弃帧，尾部余量处理最多2个目标帧。保留原画幅、尺寸与播放速度。有音轨时AAC一次编码并保持一致的原采样率及声道，不兼容音轨仍暂停。无音轨素材保持无音轨。原片保留、输出另存，合成后仍需最终内容审核。

底层统一规格实现的三份哈希快照只用于检查输入和策略未偏移；授权来源是Engine对本次绑定的有效新批准，不能用自行计算哈希替代用户授权。使用入口前运行当前脚本的 `--help`，不猜新参数。rc.6源码完整性覆盖15份运行时文件，独立验证使用自制素材、模拟供应商及渠道，不代表真实供应商或手机真人验收。

模拟结果显式标为 `simulated` 且只生成JSON清单，不能冒充MP4。真实MP4须实际探测且非零字节，回传后仍需用户确认叙事、角色一致性和音画效果；机器探测不等于视觉审美通过。

当单条模型视频的平均帧率与24fps不完全相等时，不把容器的 `r_frame_rate` 当作真实帧率，也不自动补帧或重采样。只有完整原生时间戳、帧格网及音频封装余量均通过窄范围校验时，才允许保留原时序的单输入封装，并核对输出时序；多输入仍保留原有一致性要求。实际平均帧率和验证证据写进报告，异常漂移、丢帧、粗时钟或不明音频余量停在待审。

现有真实原生VFR/AAC片段的双输入无转码诊断未通过：实验性的直接拼接会丢失中间AAC priming信息并改变接缝时间线，不能因文件可解码就放行。后续在明确许可下将同一真实片段的两个副本做统一规格，得到8秒独立实验片；机器检查及用户确认正常播放、效果可接受。它不是两个独立生成镜头，也不是rc.6新Engine验证；既有严格默认门禁继续有效。

合成失败在 `tick.blocked_reason` 返回受控原因码，并回传一条固定中文处理通知，不输出原始异常、FFmpeg stderr或素材路径。相同项目、修订、计划、素材哈希和原因只通知一次，重启不会刷屏；素材、修订或原因改变后可重新通知。此机制不绕过合成门禁，也不授权重新生成。
